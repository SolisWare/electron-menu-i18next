# Contributing to @solisware/electron-menu-i18next

Thank you for helping improve `@solisware/electron-menu-i18next`.

## Before you begin

- Use Node.js 16 or newer.
- Use npm and keep `package-lock.json` synchronized with `package.json`.
- Search existing issues and pull requests before starting overlapping work.
- Report suspected vulnerabilities privately according to
  [SECURITY.md](./SECURITY.md).

## Set up the repository

```bash
git clone https://github.com/SolisWare/electron-menu-i18next.git
cd electron-menu-i18next
npm ci
npm run check
```

`npm run check` typechecks the source, builds the package, and runs all test
suites and consumer fixtures.

## Development commands

| Command | Purpose |
|---|---|
| `npm run build` | Build ESM, CommonJS, source maps, and declarations |
| `npm run dev` | Rebuild the package when source files change |
| `npm run typecheck` | Typecheck the package source |
| `npm run test:functionality` | Test isolated public API behavior |
| `npm run test:integration` | Test integration with a real i18next instance |
| `npm run test:compatibility` | Test ESM and CommonJS package loading |
| `npm run test:consumer:javascript` | Run plain JavaScript consumer fixtures |
| `npm run test:consumer:typescript` | Compile the TypeScript consumer fixture |
| `npm test` | Build and run every test and consumer fixture |
| `npm run check` | Typecheck, build, and run the complete test suite |

Do not edit `dist` directly. It is generated by `npm run build` and is not
committed.

## Tests

Add or update tests for every behavior change and bug fix. Keep tests organized
by responsibility:

```text
test/
├── compatibility/  # Package loading through import and require
├── fixtures/       # JavaScript and TypeScript consumer projects
├── framework/      # Shared test discovery and execution
├── functionality/  # Isolated API behavior, grouped by API and concern
├── integration/    # Behavior with real external libraries
└── utils/          # Shared test utilities
```

Use one focused `test("...", callback)` case per behavior. Add a new test file
when the behavior belongs to a new concern instead of adding unrelated cases to
an existing file. Test files must end with `.test.mjs` so the test runner can
discover them.

When changing `DEFAULT_ROLE_LABELS`, compare the role list against Electron's
[current MenuItem documentation](https://www.electronjs.org/docs/latest/api/menu-item#new-menuitemoptions)
and update the role-coverage test.

## Electron examples

The basic example includes equivalent JavaScript and TypeScript variants.

The example uses Electron 43, so installing and running it requires Node.js
22.12 or newer even though the library itself supports Node.js 16 and newer.

```bash
cd examples/basic
npm ci
npm run build
npm run start:javascript
npm run start:typescript
```

Keep both variants behaviorally equivalent when changing example code. The
build compiles TypeScript and syntax-checks JavaScript.

## Code and documentation

- Preserve compatibility with Node.js 16 and newer.
- Preserve i18next 21 and newer as the peer dependency range.
- Preserve both ESM and CommonJS exports.
- Keep the package independent of Electron at runtime; use structural menu-item
  types rather than adding an Electron dependency.
- Keep public TypeScript declarations accurate.
- Preserve input immutability and existing explicit labels, including empty
  string labels.
- Always use braces around control-flow bodies, including one-line branches.
- Add `Copyright (c) 2026 SolisWare and contributors.` to new source, test,
  configuration, documentation, and workflow files that support comments.
- Use full multiline TSDoc for documented TypeScript declarations.
- Update the README when public behavior, translation keys, fallbacks,
  installation, compatibility, or platform behavior changes.

## Pull requests

Before opening a pull request:

```bash
npm run check
npm audit --audit-level=high
npm pack --dry-run
```

In the pull-request description:

- Explain the problem and the chosen solution.
- Describe user-visible behavior changes.
- List the validation performed.
- Link related issues when applicable.
- Call out breaking API, translation-key, fallback-label, or type changes
  explicitly.

Keep pull requests focused. Avoid unrelated formatting, dependency, or
refactoring changes.
